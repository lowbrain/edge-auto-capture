# Windows 実機検証

`/verify`（自動4点セット）が緑でも、それは自動検査であって実機動作の保証ではない
（CONTRIBUTING §3・§4）。このスキルは、**自動検査がそもそも通らない・検証しない領域**を
Windows + 実 Edge で目視確認し、**貼り先**（下の定義）を更新できる形にまとめる。

このスキルの目的は「手順をなぞること」ではなく、**「4点セットが緑だから動作確認済み」という
誤った報告を防ぐこと**。CONTRIBUTING §2「作業環境の注意」が挙げている、macOS では原理的に
確認できない項目（`build.ps1` / `infra._message_box_windows` の `ctypes.windll` /
`%LOCALAPPDATA%` 退避 等）が、このスキルでは逆に**主役**になる。

前提: 実行環境が Windows で、実 Edge が入っていること。macOS で呼ばれた場合は
「このスキルは Windows + 実Edge が必要で、いまの環境では実行できない」と伝えて止まる
（`/verify` の smoke `--strict` が Chrome フォールバックで PASS することと混同しない）。

## 0. 準備

```bash
git rev-parse --short HEAD
pip install -e ".[dev]"
```

- 対象コミットのハッシュを控える（貼り先の更新に使う）。作業ツリーが汚れていないか
  `git status` で確認する。
- 実 Edge のバージョンを控える（`edge://version` またはショートカットのプロパティ）。

## 1. 段階 1: 4点セット（実 Edge での実行を確認する）

```bash
pytest
python tests/smoke_badge.py --strict
ruff check .
mypy .
```

`/verify` と同じコマンドだが、ここでの狙いは緑かどうかではなく **`（起動ブラウザ: msedge）`
と出ること**。Chrome フォールバックでは実 Edge 固有の挙動を確認したことにならない。
`pytest` の `N passed / M skipped` を控える（Windows では `test_resolve_writable_dir_*` 2件が
POSIX chmod の効かなさゆえ self-skip するのが期待値 — CONTRIBUTING §2）。

## 2. 段階 2: 入口とダイアログ

- **多重起動抑止** — アプリを2つ起動し、2つ目が「既に起動しています」等で
  即座に終了すること（1つ目の保存先・log.txt を奪い合わないこと）
- **`notify_fatal` の実表示** — `config.ini` を意図的に壊す（存在しない `output_dir` の
  親を読み取り専用にする、数値項目に文字列を入れる 等）か、書き込み不可な場所を指定して、
  Windows のメッセージボックス（`MB_ICONERROR`）が実際に出ること。`infra._message_box_windows`
  は `ctypes.windll` 経由で、これは Windows でしか通らない（CONTRIBUTING §1-8）
- **終了コード** — 上の失敗時に `echo %ERRORLEVEL%`（PowerShell なら `$LASTEXITCODE`）が
  非0であること。致命エラーは `cli()` の戻り値だけで外へ伝わる設計（`__main__` は
  `sys.exit(cli())` の 1 行）なので、ここが 0 だとダイアログを出して落ちたのに
  バッチ・タスクスケジューラからは成功に見える

## 3. 段階 3: 壊れ方（意図的に壊して自己修復・退避を見る）

- **`config.ini` の自己修復** — `config.ini` を削除して起動し、既定値で
  再生成されること
- **書き込み不可時の `%LOCALAPPDATA%` 退避** — `output_dir` を書き込み不可な
  場所（例: 管理者権限が要るフォルダ）に設定して起動し、`%LOCALAPPDATA%\edge-auto-capture\`
  配下へ退避して動き続けること。**macOS では `resolve_writable_dir` の pytest はこの分岐を
  通らない**（POSIX chmod が Windows の権限モデルと違うため）ので、ここが実質はじめての確認になる

## 4. 段階 4: 機能の目視

実際にいくつかのページを開き、撮影・保存物を目で見る。

| 確認項目 | 見るところ |
|---|---|
| 索引 CSV | `index.csv` に撮影のたび行が追記され、時刻・URL・ファイル名が整合する |
| セッションフォルダと系譜 | 起動ごとに新しいセッションフォルダ、タブ系譜ごとに `lineage-*` フォルダが分かれる。ダウンロードもセッション配下に残る |
| 操作バー | セレクタ指定・撮影カウンタ/失敗表示・「フォルダを開く」ボタンが動く |
| フラッシュ写り込み防止 | 撮影の瞬間の白フラッシュ演出がスクショに写り込まない |
| 撮影中バナー除去 | 撮影直前にブラウザの通知/自動化バナーが隠れている |
| 非 HTML の扱い | PDF はページ内蔵ビューアで画像のみ保存されテキストは空（仕様どおり）、Office ファイルはダウンロードされる |

## 5. 段階 5: 配布物

配布経路は 2 つあり、**どちらも別物として両方確認する**。片方が通ってももう片方の保証にはならない。

### 5a. `pip install .`（非 editable）— #81 が報告した経路そのもの

```powershell
python -m venv .verify-venv
.verify-venv\Scripts\activate
pip install .
edge-auto-capture
```

- `pip install -e .`（開発時）ではなく、**非 editable の `pip install .`** であること。
  #81 のバグ（`badge.js` が wheel に入らず `FileNotFoundError`）は非 editable でしか再現しない
- `pip` が `Scripts\` 配下に生成する `edge-auto-capture.exe` ランチャーから
  `edge_auto_capture.app:cli` が実際に起動できること。macOS 側の検証は
  `pip wheel` で作った wheel の中身を調べ `--target` インストールで再現しただけで、
  **Windows の実ファイルシステム・pip 生成ランチャーは通していない**。ここが唯一の実地確認
- 確認が終わったら `.verify-venv` は消してよい（検証用の使い捨て）

### 5b. `build.ps1` → exe（配布用ビルド）

```powershell
powershell -ExecutionPolicy Bypass -File build.ps1
```

- exe ビルドが成功し `dist\edge-auto-capture\` が生成されること
- `dist\edge-auto-capture\edge-auto-capture.exe` を実行し、操作バーが出ること
  （#81 の受入基準そのもの）
- `config.ini` を壊すなどして意図的に失敗させ、`--noconsole` ビルドが**無言死しない**こと
  （メッセージボックスが出ること）。コンソールが無いので、ここで失敗すると
  「ダブルクリックしても何も起きない」に見える一番危険なパターン
- **`__main__.py` は `python -m edge_auto_capture` 用に絶対 import で書いてあるが、
  PyInstaller が実際にこれを問題なく凍結できるかは、5b を実行して初めて分かる。**
  ここで失敗した場合は `src/edge_auto_capture/__main__.py` の import か
  `build.ps1` の `--add-data` パスを疑う

## 報告フォーマット

`/verify` の「検証済み / 未検証 / スキップ」の3見出しに揃える。**該当が無い欄も
「なし」と書く**（欄ごと消すと書き忘れと区別できない）。段階を最後まで回せなかった場合は
「未検証」欄にどこで止まったかを書く。

```
## 検証済み（Windows実機）
- 環境: Windows <版> + 実Edge <版>、コミット <短縮ハッシュ>
- 段階1（4点セット）: pytest <N> passed / <M> skipped、smoke --strict PASS（msedge起動）、ruff 指摘なし、mypy Success
- 段階2（入口とダイアログ）: <確認できたこと>
- 段階3（壊れ方）: <確認できたこと>
- 段階4（機能の目視）: <確認できたこと>
- 段階5a（pip install . の実機経路）: <確認できたこと>
- 段階5b（build.ps1 → exe）: <確認できたこと>

## 未検証
- <段階のうち回せなかったもの・理由>

## スキップ
- <self-skip されたテスト名と理由。0件なら「0件」>
```

### 書いてはいけないこと

- 段階1（4点セット）だけ回して「実機検証しました」と書く。段階2〜5（5a/5b含む）こそこのスキルの主眼
- Chrome フォールバックの smoke PASS を「実 Edge で確認した」と書く
- 途中で止めたのに段階5まで「検証済み」に含める

## 貼り先の更新

**実行前に必ずユーザーに確認する。** GitHub Issue の編集は公開コンテンツの変更にあたるため、
無断で `gh issue edit` を実行しない。手順:

1. 上の報告フォーマットの内容をもとに、**貼り先**（冒頭の定義）の書式で下書きを作る。
   日付やコミットハッシュを主語にした一文にする（CONTRIBUTING §4 の「いつ時点かを持たせない」は
   ドキュメント・スキル側の話で、こちらは「いつ時点の検証か」を記録する側なので日付を書いてよい）
2. 下書きをユーザーに見せ、**Issue 本文への反映（`gh issue edit --body ...` 等）はユーザーの
   明示的な許可を得てから行う**
3. 貼り先の既存記述は置き換える（並べて残さない。CONTRIBUTING §4 の「二重管理にしない」方針）

## スコープ外

- **自動修正はしない。** 壊れ方を見つけたら実装側の不具合として別途 Issue 化・修正する
  （このスキルは検証と報告のみ）
- **git 操作はしない。** コミット・push は別作業
- **段階を飛ばして進めない。** 段階2〜5 はどれも「4点セットでは守られない」ことを前提に
  設計されている（CONTRIBUTING §3 の表）。時間が無い場合は「どこまでやったか」を
  正直に報告フォーマットの「未検証」へ書く

## このスキルでも救えないもの

段階1〜5（+5a/5b）を全部通しても、次は対象外。**「実機検証しました」と書くときも、
これらが検証されたことにはならない**と分かって書くこと。

- **アンチウイルス/SmartScreen の誤検知** — 貼り先の Issue で「運用事項」（技術対応の
  スコープ外）と位置づけ済み。`--onedir` で緩和はしているが、出たら都度対応であって、
  ここで PASS/FAIL を判定する項目ではない
- **企業のグループポリシー（AppLocker / WDAC）でのブロック** — 未署名 exe は
  「詳細情報 → 実行」でも回避できずブロックされる環境がある（BUILD.md 参照）。
  検証機がそうした制限下に無ければ再現・確認しようがない
- **非管理者アカウント・OneDrive/ネットワークドライブを `output_dir` にした場合の
  ファイルロック競合・同期タイミング問題**
- **英語ロケール Windows コンソールでの `log()` の表示欠落** — `tests/smoke_badge.py`
  は `sys.stdout.reconfigure(encoding="utf-8")` 済み（#3）だが、`app.py` /
  `__main__.py` 側には同じ対策が無い。`log()` は `except Exception: pass` で
  握り潰す設計なのでクラッシュはしないが、日本語ログがコンソールに出ない可能性がある
  （`log.txt` 自体は `encoding="utf-8"` 指定で正しく書かれる）。配布対象が
  日本語話者に限られる前提なので優先度は低いが、
  踏んだ場合はここが原因だと分かるように書いておく
- **長時間稼働・スリープ復帰** — 数時間単位の連続記録、PC のスリープ/復帰をまたいだ
  Edge との接続維持は、このスキルの手順では確認できない
